# Architecture

How the plugin is put together, and how the enforcement actually works.

## Layout

The plugin (`plugins/playbook/` in this repo) has four user-visible parts plus two engine directories:

- `commands/` — seven `/playbook:*` slash commands (markdown the agent executes as instructions).
- `skills/` — six harness-discoverable skill bundles, each with a `SKILL.md` (playbook patterns, judge, monitor, merge, stack, testing). The task template is rendered by `tasks/template.py`, not copied from a file; `tasks guide` prints its instructions.
- `hooks/hooks.json` — the lifecycle hook registrations (below).
- `scripts/` — executable entry points: the `tasks` dispatcher, hook scripts, `sandbox`, `monitor`, `init`, the `playbook-*` provider launchers.
- `tasks/` — the Python package behind the `tasks` CLI. The launcher (`scripts/tasks`) runs it isolated: `python3 -I`, with the plugin directory put on `sys.path` by the launch line itself, so nothing in the project's own directory can be imported in a plugin module's place (see "How the plugin's Python is started" below).
- `provider/` — provider adapters and judge-dispatch machinery ([providers](providers.md)).

Everything is plain files — bash entry points, Python 3.10+ stdlib, markdown as the runtime language. No build step, no dependencies. Python 3.10 is the declared floor everywhere (shipped modules use 3.10-only `match` syntax): every launcher refuses an older interpreter up front, and so does every hook, each with its own polarity (the task gate lets no call through but a shell command, the stop hook counts the gates without python and still blocks; the advisory ones say so and do nothing — the state echo marks the count it did not make, so the stop hook holds the turn) — and `tasks doctor` diagnoses it.

## How the plugin's Python is started

The hooks and the launchers run with the PROJECT as their working directory, and Python puts the working directory first on `sys.path` for `python3 -c …`, for `python3 -` (a program on stdin) and for `python3 -m module`. A project file named like a module such a call imports would be imported in its place: a `json.py` at the project root, a `tasks.py`, a folder `tasks/` or `provider/`. The plugin starts its own Python in two ways, each kept away from the project and from the user's Python environment in the way that fits it:

- **Inline programs and modules run isolated — `python3 -I`.** Isolated mode keeps the working directory, every `PYTHON*` variable and the user's site-packages out. The three launchers (`scripts/tasks`, `scripts/sandbox`, `scripts/monitor-lib/launch-monitor`) cannot rely on `PYTHONPATH` under it, so their launch line carries a one-line program that puts the plugin directory on `sys.path` and runs the module through `runpy` — what `-m` does. They do not put the plugin's directory on `PYTHONPATH` for what they start (task 180): its packages are called `tasks` and `provider`, and a project's own verify command was handed them in front of the project's. What you had in `PYTHONPATH` is passed on as it was.
- **Helpers run as files — `python3 -E -s <file>`.** For a file Python puts the FILE's directory first, not the working directory, so the project's directory alone does not reach them; under `-I` a helper would lose the neighbours it imports. `-E` keeps every `PYTHON*` variable out and `-s` your own site-packages: until task 180 these helpers read `PYTHONPATH`, which comes before the standard library — if yours named the project (`PYTHONPATH=.`), a project `os.py` or `json.py` was imported by them, and the destructive-command guard then exited with an error instead of blocking. All 22 shipped calls, the hook commands written into a codex configuration and the commands the merge skill gives are started this way, and a sweep in the test suite refuses a bare `python3 <file>`. Not covered: a helper you start by hand through its `#!` line; the system's site-packages; a codex configuration written before this version, until its hooks are installed again — and then only where it names the same plugin directory (the install puts the new command in the old one's place); one written by an installed older version names that version's directory and gets the new command beside the old one, as before (a known limit).

`tests/test_python_isolation.py` sweeps every shipped file for an inline program or a module started without `-I` (ledger row `PB-RUNTIME-ISOLATED`, with its bounds: the sweep reads the word `python3` and the flags after it — a call through a variable would not be seen). A consequence to know: a `PYTHONIOENCODING` or `PYTHONUTF8` you set yourself does not reach the isolated calls.

## Hooks & enforcement

Hooks enforce the structure at the OS level, because warnings don't stick — blocking does:

| Hook | What it does |
|---|---|
| `SessionStart` | Persists the session id: writes `export PLAYBOOK_SESSION_ID=<id>` into `CLAUDE_ENV_FILE` so every later Bash call this session sees it, giving each agent its own `.agent/sessions/<id>/`. It also provisions the `.claude/bin/` wrappers and sweeps dead session dirs — but it does **not** print orientation. Loading the mind map + pending tasks + CLI reference is the separate `tasks bootstrap` command, which the agent runs as its first action. |
| `PreToolUse` (matcher `Edit\|Write\|MultiEdit\|NotebookEdit\|search_replace\|write\|Bash\|Shell\|StrReplace\|run_terminal_command\|Monitor`) | The **task gate**: BLOCKS code edits when no task is active. Claude Code's Monitor runs its `command` in the same shell as Bash, so every hook here judges a Monitor as the Bash call of its command (task 307, audit 4 G1: no matcher named it, so the interlock, the gate and the folder watch never saw it, and the stop released a turn of Monitors only); a `ws` Monitor runs no shell and passes. On a shell call of `tasks work\|status\|bootstrap\|freehand\|retro\|new` it prefixes `export PLAYBOOK_SESSION_ID=<id>; ` through `updatedInput` (the call's own input, task 118), and it APPROVES (`permissionDecision: allow`) only a single plain call of this project's CLI: one line, `.claude/bin/tasks` from the project root (the hook's directory and, when the payload carries one, its `cwd`) or `<project>/.claude/bin/tasks` (a project path with no white space and none of `*` `?` `[` `]` `'` `"` `~` `#` `!`), an injected subcommand as a whole word, the file the plugin's managed wrapper (`create_wrapper`'s rule: a regular file, no link on its path, its second line `# playbook-managed`), and none of `;` `&` `\|` `<` `>` `$` a backtick `(` `)` `{` `}` `\` or NUL anywhere. Any other command it prefixes gets no decision, so Claude Code's own permission check decides, as for any command (task 301, audit 3's G5: the approval used to cover whatever was chained to the call, and any `tasks` binary). Covers Claude's `MultiEdit`/`NotebookEdit` (they edit code too) alongside `Edit`/`Write`; grok names (`write`, `search_replace`, `run_terminal_command`, `Shell`, `StrReplace`) map to Claude Edit/Write/Bash via the normalizer — the same gate path runs under every provider in code, but **supported enforcement is Claude-only** (grok/codex experimental, antigravity/pi experimental everywhere; owner decision 2026-08-21 — see the [provider support matrix](providers.md#support-matrix)). |
| `PreToolUse` on shell tools — Bash, Monitor, grok's Shell and run_terminal_command (`command-guard-hook`) | The **destructive-command interlock**: BLOCKS a high-blast/irreversible command (`rm -rf` a dangerous path, `git push --force`, `git reset --hard`, `curl\|sh`, a DB `DROP`/`TRUNCATE`) until acknowledged (run inside an `irreversible`-classified task, or the operator sets `PLAYBOOK_ALLOW_DANGEROUS=1` in the hook's environment). Conservative, and a command position is found THROUGH wrappers and their options (task 077): `sudo -u root …`, `timeout 5 …`, `chrt -f 99 …`, `stdbuf -o0 …`, `env -S '<cmd>'` and `curl … | nice -n 19 bash` reach the same rules as their bare forms, while a wrapper's query mode (`sudo --version …`, `command -v …`) runs nothing and stays allowed, and an unknown value-taking option under-blocks by design. A generic `cat evil.sh | sh` is allowed by recorded decision — only a downloader piped into an interpreter blocks; the stricter rule is a one-line `dangerous_commands` opt-in. (command-position matches, and the two whole-command rules skip only INERT data — a `cat`/`tee` heredoc body written to a plain file, and an `echo`/`printf` line redirected to a plain file with no pipe or expansion on it — so `echo "rm -rf /"` and a `cat` fixture about a piped installer are fine while `bash <<EOF`, `echo … | sh`, `tee >(sh)`, `$(…)` and interpreter heredocs are still seen — since 1.6.2 (task 199) a `$(…)` inside single quotes in a plain command of data commands is text, and a quoted heredoc that a data reader takes (`cat`, `tee`, `git commit`, `python3 - <<'PY'`) is data; the command-position rules are never masked, so a heredoc body line `rm -rf /` still blocks), fails OPEN on any internal error, config-extensible (`dangerous_commands`) / disable (`command_guard: false`). Wired on three providers (Claude via `hooks.json`, grok via its always-trusted enforcement, codex via a `PreToolUse ^exec_command$` hook), but supported enforcement is Claude-only — the grok and codex interlock paths are experimental. |
| `UserPromptSubmit` | Appends every user message to `.agent/chat_log.md` (timestamped, agent-tagged — feeds task attribution and `tasks log`). A prompt that *begins* with a harness marker (`<task-notification>`, `<local-command-caveat>`, `<command-name>`, `[SYSTEM NOTIFICATION`) is a harness event, not the user's words, and is not logged. |
| `PreToolUse` + `PostToolUse` on `AskUserQuestion` (`dialog-log-hook`) | The **options-dialog log** (task 233, PHASE-B item 6): an answered dialog becomes one `DIALOG` entry in the same `chat_log.md` — the user's answers first and exact (each its JSON string literal, `A1: "…"` — a lone surrogate escaped too, never cut —, typed notes as `Notes1:`), then the agent's questions with their headers, flattened and cut at 300 characters (`Q1 (<header>): …`), the tool call's id on the last line (a second delivery of it within the log's last 256 KB writes nothing). Every body line starts with one of those prefixes (the first `Options dialog`, the last `<!-- dialog:`), so no line is a heading, a gate or an entry header. The id and the append share one hold of the chat log's lock, waited for 3 s at most; the counter is replaced whole and never falls below the log's highest id; a run stopped mid-write leaves a fragment without a marker, after which the redelivered entry starts on its own line. The PreToolUse run (it runs before the dialog shows) starts no python: its hook-journal line marks the dialog's opening; a dialog the user cancels fires no PostToolUse (measured), so that line is its only trace. Nothing of the session's turn is touched — an answer is not a prompt. Every path exits 0. |
| `PreToolUse` (the task gate's matcher) + `PostToolUse` / `PostToolUseFailure` on shell tools (a Monitor too) and Write (`task-dir-watch-hook`) | The **task-folder watch** (task 196; since task 197 the only check of a hand-made task folder): in every lane that has `tasks/`, a task folder that appears during a session's shell call, Write or creating edit (an Edit with an empty `old_string` creates the file and its folders) and that the task registry does not know (not registered, not committed — with no registry, not committed) is flagged after the call — PostToolUseFailure too, which is what Claude Code fires after a command that exits non-zero — and that session's next edit, Write or shell call is held until the folder is removed (`rm -r`, `rmdir`) or adopted (`tasks adopt`); a `tasks` call by the CLI's path passes too, read tools never reach it, other sessions are not held. `tasks work done` refuses while the lane holds such a folder. Only the session's own lane is watched; its bounds are on the ledger row `PB-TASK-DIR-WATCH`. |
| `PostToolUse` + `PostToolUseFailure` | Echoes the gate state when it changes — the full echo when the open gate, the task or a warning changed, at a session's first call and after a session start (a compaction included), one line every 10 calls on the same gate, `{}` otherwise (task 219) — and counts every call for the stop hook's turn rules. A call that FAILS (Claude Code fires only `PostToolUseFailure` after a command that exits non-zero) is counted too — as a write only for a shell call — with no echo (task 196). A Monitor is a shell call: a write, failed or not (task 307). |
| `Stop` / `SessionEnd` | Finalize session state. SessionEnd removes the session directory only when the process is really exiting — `/clear` keeps it, because the same process continues and the active task has to survive it. |

Each enforcement decision is also appended best-effort as one JSON line to `.agent/<lane>/journal/enforcement.jsonl` — its `decision` field is one of `{allow, block, record}`: task-gate writes `allow`/`block`, command-guard/stop-hook/batch-close write `block`, and a close writes a `record` logging the verify bar it ran (a forensic record, not a gate allow/block). A second family on the same journal records **review spend** — one `hook:"review"` `record` per judge invocation (each panel seat, the single judge, the tail-cert judge), for token/effort attribution. Both are log-only and by tested construction never alter or block a decision (guarantees `PB-ENFORCEMENT-JOURNAL`, `PB-REVIEW-SPEND-JOURNAL`); the reader (playbook-lens) is a separate repo, none ships here. Since task 257 the journal rotates past 20 MB into compressed archives, each transcript's read position carried into the new file, under `journal/enforcement.lock` (appends shared, the rotation exclusive). Record shapes and rotation: [enforcement journal](enforcement-journal.md).

The task gate runs three guards before the no-active-task check — Guard 0 on a record's creation in any of the project's lanes, Guard 0.5 on edits to the active task's own `task.md`, Guard 0.6 on any task record of the project:

- **Guard 0.6 — `## Status` is the CLI's** (task 292, audit 1 G4 and item 4). An `Edit`, `Write` or `MultiEdit` of an existing task.md in one of the project's lanes — any task, not only the active one — is rebuilt into the file it would leave (matched as the Edit tool matches, as Guard 0.5 does) and refused when the CLI's own reader (`core._status_from_lines`, the last live heading's value) would read another status, when it adds a live `## Status` heading, or when the guard cannot place the edit. Every reading of the path that names an existing record in a lane is checked on its own — the text's, the kernel's, and a leading `~/` expanded first. `tasks work done` and `tasks blocked` write the status and run no hook; a `## Status` inside a code fence is content and stays editable. `tasks new` puts the intent and the name on one line, and escapes an intent's leading structure marker (`## …`, `- …`, a fence, `> …`, `<…`, past a byte-order mark) with a backslash, so neither adds a heading or a gate. Its bound: a write made by a shell command (`sed -i`, a hard link made from Bash) is not judged — the Edit/Write/MultiEdit guards' stated limit.

- **Guard 0 — manual-creation block.** A `Write` that would create a *new* `.agent[/<lane>]/tasks/<N>-…/task.md` is blocked; only `tasks new` mints task files (it owns templates and numbering). Editing an existing task.md is fine. It guards this project's records only: a task.md of another project is not refused (since task 171). The question it asks is whether the `Write` would create a file inside the project, of the path as written — read as the kernel reads it and as text, a creation under either reading counting — and the batch-close guard below has the same scope. Its bounds are stated on the ledger row `PB-TASK-MD-GUARD`: only the `Write` tool is judged. The pattern is matched on the path's text and on the path with its links followed, so a path that reaches `.agent` through a link with another name is seen too (since task 198); the batch-close guard below reads the active record from that resolved path as well.
- **Guard 0.5 — annotated batch-close.** Closing several ALREADY-DONE gates in one write — an `Edit`, a `Write`, or a `MultiEdit` (judged on the file before and after all its edits; since task 291 an `Edit` is judged on the whole file it leaves too, so a `replace_all` of `- [ ]` and a fragment that starts inside a line show every gate they tick; an Edit, and each edit of a MultiEdit, is matched as the Edit tool matches it — the text itself, else with curly and straight quotes read alike (the file's own first spelling replaced), else with `\uXXXX` escapes read as their characters, and a text replaced by nothing takes the newline after it; an edit whose `old_string` the guard cannot find in a readable task.md is refused whatever it changes — the tool would fail it, or match it by a rule the guard does not model, and no fragment can show what it ticks — and only an unreadable file's edit is judged on its fragments) — is allowed only when each newly-checked gate carries its own outcome note — since task 225 written on the lines under it, indented two spaces deeper than the gate, one fact per line (the owner's 2026-10-16 "Liste scurte de la început"); text added after the title still counts. The logic lives in `gate-batch-check.py` (shared and unit-tested; the hook delegates to it): one gate (n ≤ 1) is always allowed; a batch of 2–5 is allowed only if no line is *born-checked* (checked text with no matching open original — usually a rewritten gate) and every closed gate gains ≥ 8 non-whitespace characters of outcome — what its line gained plus what its note adds over the lines the old text already had (a note written while the gate was open, or moved from another gate, adds nothing; `283 green` passes, `done` does not); the note is the non-gate lines indented deeper than the gate (`core.gate_note_ends`, the judges' trim's rule, copied into the guard and held equal by a test); the guard reads no code fences (a fence rule there let bare ticks hide — task 225's impl round 1), so a fenced `- [x]` example inside a note reads as born-checked and over-blocks, while no fence can hide a tick; 6+ blocks even fully annotated; and a second batch with no intervening tool call blocks (kills end-of-task ticking). The helper **fails OPEN** on any internal error — only an explicit block exits non-zero — so a crashed guard never bricks the session.

The no-active-task check refuses a code edit when the session pointer is junk, stale, glob-bearing, or names a done task — and, since 1.5.45, when it names a `blocked` task (paused on a decision that is not the agent's); the refusal names `tasks work <N>` as the resume. On shell commands the gate no longer judges the text for a task directory (task 197, by the owner's answer of 2026-10-13): the check predicted from a command's text what it would create, and each repair widened a model the next review found an edge of. A task folder made by hand — by any spelling — is caught after the call by the task-folder watch above and at `tasks work done`.

**Worktrees (task 298).** Claude Code makes its worktrees inside the repository, in `.claude/worktrees/<name>/`. The gate judges a path inside one as the worktree's own path: its code needs an active task, and only its own `.agent/` and `.claude/` are exempt (task-gate-hook, and `provider.policy._is_management_path` for the codex gate). A session whose directory is the worktree (EnterWorktree, a subagent with worktree isolation) finds its project root there when the worktree's branch holds the task records (`.agent/tasks`, or a lane's `.agent/<user>/tasks`, committed — `find_project_root`), and then reads the worktree's own session pointer, so it activates its task in the worktree with `tasks work <N>`. A task active in the main tree does not open that worktree's gate. That is one lane = one worktree = one session = one task. A worktree with neither has no project root of its own: the gate walks up to the main tree, and the main tree's active task applies there (impl round 2). Records are judged by the tree that owns them (task 302, audit 3 G1): an Edit or Write of the main tree's task.md from a worktree — or of a worktree's from the main tree, or a sibling worktree's — runs the gate once more in that tree, so its `## Status`, batch-close and hand-made-record guards and the session's pointer there apply; a record of an unrelated project stays not the gate's. A session in a worktree with no pointer there is held at its stop by its task in the main tree. With no project at the working directory, a file tool's absolute target is judged in its own project.

`/playbook:init` additionally writes a **deny-list** into the project's `.claude/settings.json` blocking `TodoWrite`, `Task`, and `EnterPlanMode` — those would compete with task.md as the source of truth. If those tools suddenly error in a playbook project, that's why.

The **shell log**, `.agent/bash_history`, holds the agent's own shell commands — one line per Bash or Monitor tool call, `YYYY-mm-dd HH:MM:SS | AGENT | <command>` in local time, the command whole (`\` written `\\`, a newline `\n`, a CR `\r`), stamped when the tool call returned. The PostToolUse hook writes it from the command its payload carries (`state-echo-hook`, and codex's `exec_command` hook), through one writer, `gate-echo-lib.sh::shell_log_append`: under `flock` on the lane directory for at most a second — a writer that gets no lock writes a spool file of its own (`bash_history.spool-…`), which the next writer holding the lock appends (a host whose `flock` cannot wait, or has none, appends directly and never rotates) — and past 50 MB the file is renamed to `bash_history.archived-<date>-<pid>`. A command over 2 MiB is cut there (on a whole character, before escaping), the line says so. Hooks, the `tasks` launcher and Claude Code's shell snapshot write nothing there (task 221; until then a logger sourced through `BASH_ENV` into every non-interactive bash started with it wrote every simple command of every such shell — 45,083 lines for 1,666 commands of the agent's on one day). No reader parses it: the task windows of retro, timeline, tagger, tag and intent come from the transitions the `tasks` CLI records in the journal (`docs/enforcement-journal.md`, family 4). `/playbook:init` removes the logger an earlier version installed (`~/.claude/bash-log.sh`, its `BASH_ENV`, its rc-file lines), keeping the files as they were in its user backup; it removes all of it or none: a file it cannot look at, read or change makes init fail and restore everything (task 243).

## Per-user lanes

On a repo shared by several people (or several workstations), agent runtime state is namespaced per user so nobody tramples anyone else's sessions:

- **Legacy / single-user** — no marker, everything lives under `.agent/`.
- **Multi-user** — `.agent/current_user` names the lane, and runtime state lives under `.agent/<user>/`: `tasks/`, `sessions/`, `playbooks/`, `monitor/`, `chat_log.md`, `bash_history`.

Two files stay at the `.agent/` root by design and are **not** lane-scoped: `config.json` (shared repo policy — `merge_verify` only works if every clone sees the same declaration) and `models.json` (per-clone judge pins).

**Session directories.** Each session gets `.agent/<lane>/sessions/pid-<PID>/`, holding `current_state` (which task is active) and `counters` — the tool calls and writes since your last prompt, which the stop hook reads, and the gate the session is on; every writer of that file on the Claude lane takes `counters.lock` beside it, so tool calls the host runs side by side are each counted (task 182; the Codex lane's reset at a prompt does not take it — nothing there counts a tool call). The lock has a two-second limit; a call that was not given it is NOT counted and writes nothing to the counters, the hook says so, and the file `counts_unsure` beside them makes the stop hook hold that turn until your next prompt. Dead ones are reclaimed by process liveness (`kill -0`), never by the age of `current_state`: that file is written once at activation, so its timestamp records when the task started, not whether the session still lives. Until v1.4.7 the SessionStart sweep used that timestamp and deleted the pointer of any session more than 24h into a task — surfacing as a sudden `No active task` and blocked edits mid-task.

Every surface that reads or writes runtime state resolves the lane — hooks, the `tasks` CLI, the `playbook-*` launchers, the codex hooks, the monitor and its nudge hook, and the shell log's writer. Four rules keep that consistent:

- **The marker is exactly one line.** A trailing CR is stripped (CRLF markers work), surrounding whitespace is ignored, and a missing final newline is fine — but a *second* content line is invalid, not "use the first one". Otherwise `alice\n../evil` would resolve to lane `alice` in the shell readers while Python rejected the same file.
- `.agent/current_user` is **gitignored and install-local**, so it never arrives with a clone. On a fresh clone of a multi-user repo — lanes present, marker absent — nothing is allowed to invent a lane. Surfaces you invoke directly (`tasks new`, `tasks init`, `/playbook:init`, the `playbook-*` launchers, the monitor) **fail loud**; hooks, which must never take a session down, **skip quietly** and `session-start-hook` prints a warning. Enforcement still fails closed: with no knowable lane there is no active task, so edits are blocked. Fix: `echo '<your-username>' > .agent/current_user`.
- A **malformed** marker is never treated as "use the root" — not for writes and not for reads. State-creating surfaces refuse; the hooks (the shell log's writer among them) and the nudge hook skip silently; the provider adapters report *no active task* rather than falling back to root state (a stale root task must not be able to satisfy the gate); the Codex hooks apply their per-event policy — PreToolUse fails closed, the rest fail open.
- A repo that has *both* root `.agent/tasks/` and per-user lanes is a legitimate mixed layout — root is itself a lane — and is left alone.

**Upgrading an existing install:** `.claude/hooks/monitor-nudge.sh` (per project) is a *copy* that lives outside the plugin and keeps its old contents until you re-run `/playbook:init`. Re-running init also removes the BASH_ENV shell logger versions up to 1.6.x installed (`~/.claude/bash-log.{sh,zsh}`, `BASH_ENV` in `~/.claude/settings.json`, the `# claude-playbook: command logging` lines of `~/.profile`, `~/.bash_profile` or `~/.zshenv`): until then it keeps writing every shell's commands into the same `bash_history`, beside the hook's lines. A desktop session keeps an exported `BASH_ENV` until you log in again; bash ignores it once the file is gone.

## Task system

Every task directory the CLI makes is named in its lane's task registry (`.agent[/<lane>]/task-registry`, beside `tasks/`, machine-local; `tasks/registry.py`): the creators reserve a number, build the directory under a temporary name in the lane and rename it in, under one per-lane lock that also takes the number, and `tasks adopt` registers a folder the CLI did not make (a renamed one). A lane that has `tasks/` and no registry gets one at a session's start and at `tasks work <N>`, enrolling what stands (task 197). It is the provenance the task-folder watch and the close read (`registry.unknown_now`; PLAN §S14 T5b, task 196); its bounds are on the ledger row `PB-TASK-REGISTRY`. A task is a directory under `.agent/tasks/<N>-<type>-<name>/` (or `.agent/<user>/tasks/…`) whose `task.md` is both the plan and the execution trace: Design Phase gates (understand → structure → reflect → verify) → judge review → Work Plan gates → implementation review → pre-review. State lives on disk, keyed by a PID-based session ID that works across providers — which is why tasks survive context compaction and session restarts, and why two agents can hand a task off through the file alone.

The final pre-review gate asks for the mind map to be updated by editing the **owning subsystem node in place** — a new node only for a genuinely new subsystem, never one node per task. Without that rule a long-lived map grows into an append-only changelog of tasks; with it, what you learned lands where the next reader will actually look for it.

## The monitor

A second Claude process that watches the front agent's session transcript incrementally and posts nudges through a hook when the trajectory goes wrong. Separate context window — it judges from outside, without the front agent's anchoring. Components: `.claude/bin/monitor` (wrapper), the plugin's `scripts/monitor` + `monitor-lib/`, and per-project rules under `.agent/monitor/` — or `.agent/<user>/monitor/` on a multi-user repo, where each user gets their own monitor state (scaffolded by init).

## The sandbox

`.claude/bin/sandbox` runs the agent with `--dangerously-skip-permissions` inside OS-level containment: **Linux bubblewrap** with deny-write-by-default (Linux only since 2026-10-08; the macOS seatbelt backend belongs to 1.5.47, branch `multiplatform`). It needs bubblewrap: where `bwrap` is not installed, or is installed but cannot start a sandbox, `.claude/bin/sandbox` refuses to launch the agent — exit 2, with the reason and, when it is missing, how to install it — instead of running it uncontained; the `--print-argv` preview is refused the same way, and `monitor start` by a pre-flight, before it writes anything. A `bwrap` reached only through a relative `PATH` entry counts as missing: a launch runs in the project directory, where such an entry can name a file of the project. Inside the sandbox the project is writable and its git metadata is not — whatever an extra `--rw` path covers: the `.git` directory, or the `.git` file of a linked worktree or submodule with the git directory and common directory it leads to, for the project and for every repository `code_roots` names, are bound read-only after every writable bind (since task 169; before it `--rw <project>` made `.git` writable again, a worktree's `.git` file could be re-pointed, and a nested repository's `.git` was writable). A git directory that CONTAINS the project — worktrees kept inside a bare repository — is bound read-only before the project, and the entries git keeps in it (recognised by name, from git's repository layout) again at the end, so the project stays writable. Git's hooks and settings are kept read-only wherever git is TOLD to take them from (task 181; this protection requires a host that prevents nested user/mount namespace creation): at launch the sandbox asks git for its hooks directory (`core.hooksPath`, or `.git/hooks`, which may be a link), for every settings file in effect and for every `include`/`includeIf` path, for the project and each `code_roots` repository, and binds those places read-only last — what an agent writes there would run on your machine at the next git command. Every directory the run could write between a writable area's root and a place that is kept — git's own directories of a nested repository included — is bound onto itself first, so that it cannot be moved aside and replaced from inside (a read-only bind fixes its own path only). What an include that does not hold names is read from the file itself. The repository's own settings files and the system's and your own are named explicitly, where the environment of the launch puts them (`GIT_CONFIG_SYSTEM`, `GIT_CONFIG_GLOBAL`, `XDG_CONFIG_HOME`, `HOME`), even when they are empty or do not exist yet, and so is an include the environment names (`GIT_CONFIG_COUNT`): an empty one is kept read-only, and a missing one in a place the run could write refuses the launch until you create it (empty will do) — a `HOME` under `/tmp` is such a case, until both `~/.gitconfig` and `~/.config/git/config` exist there (one refusal names both). All core.hooksPath values are protected even when shadowed, and direct hook files and their symlink targets are included. Unresolvable sources refuse launch, and so does a regular source file with multiple hard links that you could write or make writable — another name of it could be writable in the sandbox, and the other names are not looked for (a `cp -al` copy of a repository is refused until its settings file and hooks are copies of their own); a file of another owner that you cannot write, such as `perl` under its two names, does not. Pins extend to the outermost covering writable area; a directory is fixed only where the run could write it — inside a read-only place nothing can be renamed, and nothing there is bound writable: in a `--ro-project` run only the `--rw` paths are — and one that holds a later project bind or record mask is pinned before it, so those restrictions remain effective. A real probe of the selected bubblewrap runs once per launch: where --disable-userns works, every launch adds --unshare-user --disable-userns, which --rw-git-sources cannot lift — and then nothing inside the sandbox can create a user namespace (a nested `bwrap`, `unshare -U`, a rootless container fail there; Claude and Codex judges were measured to start and answer under bubblewrap 0.8.0). Where it does not work (including bubblewrap 0.6.1), launch and --print-argv proceed with one stderr warning naming the nested user/mount namespace limit and the remedy, non-setuid bubblewrap >= 0.8.0. In this compatibility mode a nested namespace can detach the protected tree and replace Git metadata (measured); the owner chose this conditional behavior. Cases that cannot be kept refuse the launch, saying what to do: a place that does not exist where the run could create it; one that is, or contains, a path the run must write; one reached through a link in a directory the run may write; a repository where git cannot answer (a settings file it cannot read); and, in a read-only run that hides the conversation records, one that is in or over a hidden place — a hooks directory that is a directory above the project would be laid over what hides them. `--rw-git-sources` is your explicit permission to let an agent edit them (it is not available with `--prompt`, and the refusals of a read-only run, which every review is, do not name it). Not covered: what a kept hook sources or runs from the project (the husky layout: the stub in `.husky/_` is read-only, the `.husky/pre-commit` it sources is project content); a nested repository that `code_roots` does not name; a `.git` that is a symlink; attribute and ignore files; a setting changed on the host while the run is under way (git is asked once, at launch); a git that is later run on the host in another environment than the launch's (other `GIT_CONFIG_*`, `XDG_CONFIG_HOME` or `HOME`). With `--ro-project` the project is read-only too and only the `--rw` paths take writes; an `--rw` path that overlaps a place where the conversation records are hidden — `.agent` (whether or not it exists yet), the directory behind a symlinked lane, the target of a record that is a link: a path that covers it, is it, or lies inside it — is refused before anything starts, and `--keep-records` is the way to have one (the monitor's `.agent/monitor`). Judges are not launched through that command: without bubblewrap a review still runs, uncontained, says so, and the tamper guard is then its only defence. This is **write** containment, not a read or network jail — "read-only" here means writes are denied, nothing more. The whole filesystem stays *readable* (bubblewrap mounts `/` read-only, it does not hide it), and the network stays reachable **by design**. One exception, for a **read-only (judge) sandbox only**: the conversation records — `.agent/chat_log.md`, `.agent/sessions/`, `.agent/bash_history` and their rotated/archived copies, in `.agent`, in each lane under it and behind a symlinked lane — cannot be read, including ones created or renamed into place while the judge runs (bubblewrap shows `.agent` and each lane as an empty tmpfs with only the non-record entries bound back, `/dev/null` standing in for each record that existed at launch; task 125, owner decision 2026-10-02; task 138). The conversation monitor runs read-only too but passes `--keep-records`: it reads the session's transcript pointer. Records more than one lane level deep, the agents' own transcripts under `~/.claude/projects/`, and `.agent/monitor/` are not masked. Nor is anything in a project that has no `.agent` directory when the run starts: there is nothing to mask, so records written into an `.agent` created during the run can be read (measured, task 169; a review always has one — its task record lives there). What's enforced at the kernel level is: the project directory is writable, `.git` is read-only (history can't be mangled), and writes *outside* the project are denied — reads and network access are not. Network isolation exists only as an explicit opt-in (`bin/sandbox --no-network`, which adds bubblewrap's `--unshare-net`), and it is never used for judges, which must reach model APIs. Honest caveats, about what that refusal does not cover. A launch nested inside a sandbox is not wrapped again: it relies on the outer one. The signal for "nested" is the environment variable `PLAYBOOK_SANDBOXED=1`, which the sandbox gives only to a child it wrapped; set by hand it is the operator's own statement that an outer cage exists, and nothing checks it. And a judge on a host without bubblewrap runs with bypass flags and **no** kernel containment (the review prints the warning); where `bwrap` is installed but cannot start (e.g. unprivileged user namespaces restricted), a judge fails to launch — it does not fall back. `tasks environment` reports both conditions. Pairs with the task system for the "two agents, one task" pattern: orchestrator outside, worker inside, task.md as the handoff.

## Judges

Blind by construction: a judge gets the repo but not your conversation, so it can't anchor to whatever was already agreed in chat. Single judge (`plan-review` / `impl-review`) writes findings into the task.md; the panel (`panel-review`) fans out to every seat in `models.json` in parallel and writes `judge.md`. Judge output is triaged, not obeyed — the task template's review gates require an accept/park/reject decision per finding. **Post-D6 protocol (task 108):** both context builders put a SETTLED block first (the project's owner rulings in force from `.agent/rulings.md` — task 227: whole entries within 4,000 characters, the rest named; a taskless panel gets them too — then the task's `## Owner rulings` + earlier `REJECT` triage lines; past 8,000 characters it is cut on a line and says how many lines it left out); each panel round's `Panel-snapshot` carries, per scope, a `base` tree of the working state (`tasks/post_d6.py::worktree_tree`, temporary `GIT_INDEX_FILE` + `git write-tree`); an `impl-review` after an impl panel reviews base → working tree, computes `POST-D6 VERDICT` from tagged findings and is capped at two runs per panel (a third only with `--owner-ok --reason` (since 1.6.3, task 209; until then a counted Critical in run 2 opened it)). No ref keeps a base alive — objects live until `git gc`.

**judge.md round format and retention.** Each `panel-review` run prepends one round to `judge.md`, newest first. A round starts at a `# Panel Plan Review` or `# Panel Impl Review` heading and runs to the next such heading (or end of file); the close gate reads only the newest round's `**PANEL VERDICT: …**`. Since 1.6.2 (task 200) the line after the heading is the writer's mark `**Round-format:** 2` and every line a judge wrote is quoted (`> `), so a judge cannot open a round or supply a header field. Every heading opens a round, as before — the rounds 1.6.1 wrote, above or below the 1.6.2 ones, stay rounds — and a round is format 2 only in the LEADING run of marked headings (1.6.2 stacks newest first, so a mark after an unmarked heading is a line 1.6.1 let a judge write) — a provenance label, which no reader decides on; a round's verdict, tree-state, round id, snapshot and tamper receipt come from its header only (the lines before its first `═` bar), each at a line start. The stacker keeps any text above the first heading ABOVE it — never counted, never archived (it used to drop it; 1.6.1 still does, so after a rollback a note written there is lost at its next stack — write notes at the END of judge.md) — and refuses to replace a judge.md it cannot read. `judge.md` retains the newest `JUDGE_MD_MAX_ROUNDS` (5) rounds — the review-read budget. Since v1.5.41 any older round that overflows that window is **archived** (its round content preserved as UTF-8 text) to a sibling `judge-archive.md` (newest first, never deleted — the same "moving history is not deleting it" contract as `task-archive.md`), and `judge.md` carries a one-line pointer to it. Earlier releases dropped the overflow with only a "…full history is in git" note, which was unreliable (judge.md is rewritten in place and committed at most once per task, so intra-session rounds were lost); the archive fixes that. **The true panel-round count for a task is the machine-written round headings in `judge.md` plus those in `judge-archive.md`.** Note two edges: (1) the 5-round cap on `judge.md` holds only when the archive write *succeeds* — if archiving fails, *this* call's overflow is kept untrimmed in `judge.md` (it may exceed 5) rather than dropped, while any rounds already moved out in earlier successful archives stay in `judge-archive.md`; no paid round is lost, and the true count is still the headings in **both** files (never `judge.md` alone); (2) in a round 1.6.2 writes a judge cannot emit a `# Panel … Review` line at all — its lines are quoted — so the count is the writer's; in text 1.6.1 wrote, a judge that emitted such a line at the start of a line was counted as an extra round, and still is (the writer's mark, `**Round-format:** 2`, and the quoting are the delimiter that the lens-v0.2 caveat asked for — task 200).

**The run ledger keeps how each panel ended (task 232, PHASE-B item 6).** A panel reserves its run in the task's
`post-panel-reviews.jsonl` before its tamper snapshot and finishes it with a `done` record on every exit the process
lives through (its `finally`; a SIGKILL, or a SIGTERM no handler turns into an exit, leaves the reservation without one,
as before — PLAN.md's SIGTERM input). That record
says how the panel ended — `outcome`: `completed` (the round is in judge.md — a below-quorum FAIL and a dead-pin stop
included), `void` (the tamper guard voided it, before judge.md), `unsaved` (judge.md could not be written) or
`incomplete` (any other exit after the reservation: a crash, an interrupt) — and, for a completed round only,
`measures`: `round_id` (the round's `**Round-id:**`, which is the reservation's id), `verdict`, `succeeded` of `seated`
judges, the `quorum`, and the `critical` / `important` findings the judges wrote (or `counts_error`, why they could not be
counted — the verdict fields stand), counted on the round as written by the
stop rule's own reading (`stop_rule.round_findings`: quoted judge lines only, `[SETTLED]` not counted, each judge's
line counted as written — no merging across judges). `status` stays `done`, and the post-D6 runs' flat keys
(`verdict`, `critical`) are never written on a panel record, so no reader of the ledger changes.

Since v1.4.3 the judge runs write-denied: the project is mounted no-write, so a judge physically cannot edit the repo or task.md. It is not otherwise isolated — it can still read the filesystem and reach the network (which it needs, to call model APIs); "read-only" here means writes are denied, nothing more. Because that OS containment is not always available (`bwrap` not on PATH, or a nested sandbox), a working-tree tamper guard backs it up — the review paths snapshot git status + the task.md hash before and after, and if a judge changed anything the review is saved with a loud TAMPER banner, ingestion is refused, and the run exits non-zero.

**Judges read a fixed copy of the tree (task 231, PHASE-B item 7).** Before the judges of a panel or a single
review start, the CLI copies what git lists — the outer repository and each `code_roots` repository, each a
`git clone --local --mirror` with the live config, index and listed files (`tasks/review_view.py`) — into
`<lane>/journal/review-views/`, and keeps the copy only when it is sealed by content: its fingerprint equals the
stamp taken from the live tree, each scope's working-tree object equals the snapshot's base (for the post-panel
judge, its delta's tree) and HEAD is the same. bubblewrap then mounts the copy read-only AT the project path
(`sandbox.ProjectView`), so the judges see the same paths as task.md while the agent writes the live tree; what git
ignores is bound from the live tree at its own path, as the judges always saw it, and `.agent`'s record masks are
built from the live `.agent`, its other entries bound back from the copy (tracked) or the live tree (ignored). The
tamper guard then watches the copy; the stamp is the sealed fingerprint and the snapshot is the one taken before
the spawn, so a live tree that moves on purpose is not "moved". The recorded snapshot must be the copy's own (each
scope's commit, base and dirty map); the copy is frozen read-only on disk; records are never copied and the copies
folder is hidden from the judges; the judge runs in a PID namespace of its own and the folders above the project are
pinned. The ready line comes right before the judges start, after everything the review reads from the live tree (the
config and its quorum, the prompt, the chat log). A copy that cannot be sealed while the live tree did not move reads
the live tree, said first. No copy is possible inside a sandbox, without
bubblewrap, for a project in a subdirectory of its repository, a linked worktree, a linked `.agent` or lane, a
linked code root or one outside the project or not the top of its own repository, a submodule or untracked nested
repository, a listed special file, a scope with no commit yet or with unmerged entries, an ignored entry that
overlaps a code root, task records git ignores, a `fingerprint_exclude` that hides code, an unignored journal, or
more than 50,000 listed files / 1 GiB / 2,000 ignored entries — the review then says so first and reads
the live tree under the guard below. A tree that keeps changing while its copy is made (three times) refuses the
review before anything is spent. Tail certification still reads the live tree: the close certifies the current
tree and discards a PASS if it moved.

**What the guard sees, and what a degraded guard means (v1.5.45).** Its scope is
the outer tree's porcelain state, the content hash of every dirty/untracked file,
`task.md`'s own hash, the task directory's git-independent identity (realpath +
inode + symlink-ness, so a judge cannot swap it for a symlink and redirect the
trusted parent's later writes), and — when `code_roots` is set — each nested
repo's state plus its resolved identity. Dirty files are opened at the **git
toplevel** and named **project-relative**, so a project living in a subdirectory
of a larger repo is guarded correctly (before v1.5.45 those paths were joined
onto the project root, which made content-only edits invisible and `monitor/`
churn a false alarm).

Findings split in two. A **mutation** — a porcelain or content-hash change, a
task.md rewrite/deletion, a task-dir or code-root identity change, a `.git` that
disappeared, or an errored guard — still prints the loud TAMPER banner, refuses
ingestion and exits non-zero. A **caution** is the guard telling you it could not
fully run, or naming something a judge could not have done: `git status`/`-z`/
`rev-parse` failed (on one side or both — the `.git`-removed banner needs the
repo to have actually disappeared, probed independently of `git status`), or
HEAD moved during the review. Where an OS sandbox is actually denying judge
writes, a moved HEAD is a concurrent actor: it is a caution, and so are the
porcelain lines that commit removed — but only for the paths the commit itself
touched, and anything it cannot explain (a new file, a changed content hash)
still hard-stops. Where there is **no containment** (no `bwrap` on PATH, or an already
nested sandbox) a judge that can write can also commit, so a moved HEAD is a
MUTATION there. A caution about a concurrent commit does not mark the round
degraded: the guard worked, the tree moved, and freshness already covers that. A
caution no longer discards the paid review — the verdict is kept, the notice is
printed, and the round records `**Tamper guard:** degraded — <what>` (or
`clean`). That receipt is load-bearing: a close held to the high-consequence bar
(assertive, irreversible, or an unclassified `## Risk`) **blocks** on such a
round with `TAMPER-GUARD-DEGRADED`, with the same two exits as a stale panel
(re-run the panel, or `--stale-panel-ok --reason "..."` recorded in the receipt — since 1.6.3 the review stop rule
needs the post-panel judge's PASS or `--owner-ok` instead wherever a guard list or an irreversible task's automatic
judge applies, docs/configuration.md, "The review stop rule");
`reversible` closes proceed with an advisory. Tail certification refuses
outright. The single-judge path carries the same receipt in its judge log and in
the findings it writes into task.md; when no panel round carries a close, the
close reads that log and records the degradation as an advisory receipt clause.

The task's own record directory stays exempt from the working-tree diff, scoped
by whether `task.md` itself is tracked: an **untracked** task.md means the whole
directory is the panel's fresh record dir (broad exemption), while a **tracked**
one exempts only newly created (`??`) record files by name (`judge.md`,
`judge-archive.md`, `judge-*.log`, `task-archive.md`, `vetting-ledger.json`) —
a rogue rewriting a committed `judge.md`, or dropping an `evil.py` beside it,
still flags. task.md content stays guarded by its hash regardless.

**Session-pointer isolation (v1.5.41).** A review or probe spawn runs as a child process that would otherwise inherit the foreground session's identity — `CLAUDE_ENV_FILE` plus the `CLAUDE_CODE_*` / `CLAUDE_PID` vars — and could shadow which task is active, surfacing as a spurious `No active task` during a background panel. Every spawn on the review/probe paths (panel and single-judge reviews, `run_subagent`/`stream_subagent`, and the `claude -p` model-availability probe) now scrubs those parent-session vars through one shared scrubber; writable subagents additionally pin an isolated per-invocation `PLAYBOOK_SESSION_ID`, while read-only judges share a fixed non-foreground `judge` identity (harmless — they cannot write a pointer). Guarantee `PB-SESSION-POINTER-ISOLATION`.

**Task records are written in transactions (v1.5.45).** `tasks/atomic.py` makes
each write all-or-nothing; `tasks/filelock.py` makes the whole
read → transform → write indivisible. The gap was measured, not assumed: the
real close shape — read task.md, run the verify contract for minutes, then write
the receipt — lost a concurrent `tasks blocked` in **5 of 5** trials, leaving the
task `in_progress` with no `## Blocked` section at all.

Three rules define the boundary:

* **Writers serialize, readers never do.** Every read-modify-write of task.md /
  judge.md goes through `atomic.rewrite(path, transform)`, which holds a
  per-task advisory lock (`fcntl`, else a loud unlocked degrade) on a
  persistent sibling `<name>.lock`. `tasks status`, the gate hook and the
  state-echo hook read on every tool call and take no lock — waiting on a
  minutes-long close would stall the session, and `atomic_write` already
  guarantees they never see a torn file.
* **One transform per VERB, not per helper.** A close is receipt *and* status; a
  handoff is section *and* blocked; a resume is status *and* its stamp. Each is
  composed on the bytes just read and written once, so the pair can never
  half-land. The expensive work (verify, judges) happens outside the lock.
* **A commit re-checks what earned it.** `core.compose_close` refuses — leaving
  task.md byte-identical — when a `## Blocked` appeared, the status moved, or
  the newest panel round changed (its header *or* its findings, since task 085)
  while the close was running, and the close also compare-and-swaps the tree
  fingerprint its freshness decision was made on. Routing alone would not have
  been enough: with the lock neutered the first regression still passed, because
  each writer now reads late; what closes the window is the refusal.
  The other transitions check their source the same way (task 085): blocking
  or handing off refuses a task that is already done, and resuming refuses a
  task that is not `blocked` — so a close that commits first is never
  overwritten by a block or resume that was waiting behind it.

Two-file protocols (`stack_judge_round`'s archive-then-judge.md, `tasks compact`'s
archive-then-task.md) keep their own rollback and hold the lock across the whole
sequence. `tasks tag` rewrites `chat_log.md` while the chat-log hook appends to
it, so it rendezvous on the hook's own lock file **and** compare-and-swaps the
content — it refuses rather than drop a prompt. The chat-log hook and the
options-dialog hook each take the next id and append under ONE hold of that lock
(task 233 — the chat-log hook used two holds before, so a dialog's entry could land
between a prompt's id and its text), and the readers take an entry header only at
the start of a line. The destructive-command guard
deliberately takes no lock (a hook must never wait on a writer): it reads the
task once for status and risk, then re-reads the session pointer, and every
error keeps the command blocked.

Honest bounds: the lock is ADVISORY, so a process that writes task.md without
the primitive is not stopped (a structural test fails the build when a new
unapproved writer appears in the package); it is per-task-directory, so it says
nothing about a network filesystem or another machine; and the whole-tree
freshness TOCTOU remains detection-only — a task-directory lock cannot serialize
edits to arbitrary source files during a judge call.

## CI

`.github/workflows/verify.yml` runs `scripts/verify` on two Linux lanes on every push and pull request — py3.10 and py3.12 — with bubblewrap installed first so the live sandbox tests run there (since task 158; they skipped before). (Until task 221 each lane also ran the zsh shell logger against the four lane shapes; that logger is retired.) Playbook is **Linux only since 2026-10-08** (owner decision, which supersedes D1 (b) of 2026-09-24, "all four lanes on every push"): the macOS and Windows/Git Bash lanes are gone, and the last version they tested is 1.5.47 — tag `last-multiplatform`, branch `multiplatform`, whose workflow still has them (`git show last-multiplatform:.github/workflows/verify.yml`). Both Linux lanes must be green for a release, and that is **required by the release checklist (W12), not by GitHub**: `main` has no GitHub branch protection (`gh api repos/{owner}/{repo}/branches/main/protection` returns 404, measured 2026-09-25), so nothing on GitHub stops a push that has not passed. Nobody waits on the lanes synchronously — push, then check the run at the next gate that needs it (`gh run watch <id>` inside a background Monitor, or `gh run view <id>` on return). Owner decision D2 (b): a release may rerun once for a disclosed flake whose failure capture is saved into the release record. `concurrency: cancel-in-progress` means a superseded push gets no verdict.

Full failure evidence: with `PLAYBOOK_VERIFY_FULL_LOG=<file>` set, `scripts/verify` appends every child command's complete output — unittest at `-v`, and each shell fixture's full transcript, including the run inside unittest — to that file. It is the failing run's own output. The Windows lane set it (task 096) until the lane was removed on 2026-10-08; the Linux lanes do not, and a local run can.
